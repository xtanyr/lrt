# Проверка LRT по roadmap documentation

Дата: 14 сентября 2026. Проверены исходники backend/frontend, схема Prisma, миграции, seed, конфигурация запуска и тесты. Основание: документы 01–12 из `C:/LRT/roadmap documentation`.

## Вывод

Проект — частичная реализация с большим количеством экранов и серверных заготовок. Он собирается, но пока не обеспечивает полный цикл «вход → отчёт → корректный рейтинг → история → контроль города». По обнаруженным расхождениям ни одну фазу 0–7 нельзя принять целиком по критериям документа 11. Это не означает, что работа отсутствует: основная структура приложения и БД уже создана.

Процент готовности не приводится: количество файлов и экранов не измеряет работоспособность, а трудоёмкость оставшихся задач не оценивалась.

Слово «реализовано» ниже означает наличие конкретной логики в исходниках; готовность сквозного пользовательского сценария оценивается отдельно. Проверка работающего приложения с реальной БД, Google OAuth и реальными историческими файлами не проводилась. База данных не изменялась; миграции и seed не запускались. При сборке обновились генерируемые артефакты. Исходный код приложения не исправлялся.

## Что уже реализовано

- NestJS backend, React/TypeScript frontend, Vite, npm workspaces; обе сборки проходят.
- Prisma/PostgreSQL: города, кофейни, пользователи, привязки many-to-many, отчёты, значения метрик, вопросы анализа, комментарии, логи, настройки цветов, ИПВ, исключения, уведомления, токены сброса. Есть миграции и seed.
- Категории кофеен и таблица индивидуальных порогов заложены в модели. Есть флаг закрытия кофейни и архивирование метрики через `isActive`, без физического удаления в соответствующих сервисных методах.
- Механика хеширования паролей, JWT, стратегии local/Google, guards ролей и маршруты интерфейса.
- API черновика, отдельных значений и ответов анализа, отправки отчёта; проверка `isLocked` в части операций.
- Серверная оценка отдельных метрик по двум порогам, направлению и трём зонам, использование Decimal.
- Экраны отчёта, результатов, методики, города, кофеен/городов COO, метрик, структуры, пользователей, конфигурации, истории и импорта.
- API изменения статусов ИПВ и ручных исключений; хранение уведомлений.
- Импорт xlsx с предварительным просмотром, выбором кофейни/периода и ручным исправлением значений в UI.
- Набор автоматических тестов: 29 backend unit, 2 в каталоге integration, 10 frontend.

## Статус фаз плана

### Фаза 0. Фундамент — частично

Есть стек, схема, миграции, вход, guards и layout. Не завершены согласованная авторизация, привязка данных к текущему пользователю, полноценное разграничение доступа. В папке не найдены Git-метаданные, CI workflow и инструкция запуска. Это вывод о предоставленной копии, а не о возможном внешнем репозитории.

Для приёмки: вход под каждой из четырёх ролей должен открывать именно назначенные объекты, а попытка доступа к чужому отчёту — отклоняться сервером.

### Фаза 1. Кабинет лидера и рейтинг — частично, основной блокер

Есть каркас пяти разделов отчёта, API сохранения и отправки, экран результатов с графиком и методика. Не готов полный состав формы, сохранение плановых значений, создание первого черновика, редактирование после отправки, корректные сроки, аудит изменений, единый расчёт и неизменная история.

Для приёмки: новая кофейня должна провести месяц без предварительного создания отчёта через seed; все значения и ответы должны пережить перезагрузку; рейтинг должен совпасть с эталоном из документа 03.

### Фаза 2. Лидер города — частично

Есть список/карточка кофейни, чтение метрик и комментариев. Контроллер дашборда передаёт пустой список городов. Карточка не даёт редактировать полный отчёт, загружает только текущий календарный месяц. Полный просмотр анализа с подсветкой пропусков и датой подачи именно в московском времени не завершён.

Для приёмки: лидер с несколькими городами видит все назначенные кофейни, выбирает период и правит разрешённое поле с записью автора изменения.

### Фаза 3. COO — частично

Есть страницы по кофейням, городам и отчётам, элементы сортировки. Расчёт рейтинга повторён во frontend и не соответствует спецификации. В городском разрезе нет полноценной динамики каждой метрики за 12 месяцев; вместо неё — средний итоговый балл последних отчётов. Нулевые рейтинги исключаются из среднего, периоды разных кофеен могут смешиваться. Цвета захардкожены. Просмотр конкретного отчёта ищет по имени кофейни и месяцу без года.

Для приёмки: сводки должны использовать общий период, учитывать заполненный месяц с нулевым рейтингом и получать значения из единого расчёта/снапшотов.

### Фаза 4. Админка — частично

Есть управление метриками, добавление городов/кофеен, деактивация кофеен, изменение ролей и нескольких назначений, изменение цветовых границ, экран истории. Но поля настройки метрик расходятся с полями серверного расчёта, история автоматически не записывается, основные страницы недоступны COO. Настройки исключений по стажу, полноценное редактирование триггеров в UI, управление категориями и общими ссылками не завершены. Управление пользователями в UI в основном ограничено ролями/назначениями; полного создания и изменения имени/email нет.

Для приёмки: COO/админ меняет параметр через UI, изменение действует в новых расчётах и появляется в журнале, история прошлых месяцев сохраняется.

### Фаза 5. Мониторинг ИПВ — автоматический движок не реализован

Есть модели, чтение/изменение статусов и исключений, экран. Нет вычисления T1/T2/T3 по истории, проверки роста/стажа/утверждения, применения исключений, создания событий и связанных уведомлений. Не завершён даже сквозной ручной сценарий из-за несовпадения маршрутов и статусов.

Для приёмки: искусственная последовательность рейтингов вызывает нужный триггер; флаг и стаж подавляют его; запуск/завершение ИПВ меняет индикаторы; после 14 дней показывается просрочка.

### Фаза 6. Исторические данные — частично

Есть инструмент импорта, но его формат не соответствует описанному мастер-листу «Метрики». Парсер повреждает дробные числа с запятой. Импорт не рассчитывает/не фиксирует исторический рейтинг и может обновлять существующий закрытый отчёт. Перенос реальных данных и сверка с Google Sheets не подтверждены.

Документ 08 относит миграцию к отдельной задаче после запуска, документ 11 включает её фазой 6. Поэтому отделять готовность самого импорта от обязательности переноса всех данных до первого запуска.

### Фаза 7. Проверка и стабилизация — начата

Сборки и существующие тесты проходят. Нет подтверждённой приёмки всех четырёх ролей, API-тестов с настоящей тестовой БД, UAT на 2–3 реальных кофейнях и проверки мобильной версии. Docker Compose описывает только PostgreSQL: комплект развёртывания backend/frontend/reverse proxy не найден.

## Конкретные проблемы, которые блокируют приёмку

### 1. Вход и идентификация пользователя не согласованы

`POST /auth/login` возвращает accessToken в JSON, frontend посылает его в `Authorization: Bearer`. JWT strategy читает только cookie `accessToken`, которую обычный login не устанавливает. В чистой сессии последующие защищённые запросы будут отклоняться.

JWT strategy возвращает `id`, но контроллеры отчётов, дашбордов, комментариев/уведомлений используют `user.sub`. В результате идентификатор отсутствует там, где нужен для фильтрации/авторства. Google strategy возвращает результат `login` вида `{accessToken, user}`, а callback снова передаёт эту обёртку в `login` как пользователя. Frontend также не восстанавливает Google-сессию через `/auth/me`.

Источники: [JWT strategy](C:/LRT/backend/src/auth/strategies/jwt.strategy.ts:11), [auth controller](C:/LRT/backend/src/auth/auth.controller.ts:26), [Google strategy](C:/LRT/backend/src/auth/strategies/google.strategy.ts:36), [API client](C:/LRT/frontend/src/services/api.ts:9), [auth provider](C:/LRT/frontend/src/contexts/AuthProvider.tsx).

Сброс пароля создаёт токен, но лишь печатает его в console вместо отправки письма. JWT настроен на 60 дней, refresh endpoint есть, но frontend его не вызывает. Наличие срока токена само по себе не реализует скользящее продление всей сессии.

### 2. Права роли не обеспечивают доступ только к своим данным

Методы чтения и изменения отчёта по ID/coffeeShopId допускают все четыре роли, но не проверяют принадлежность кофейни пользователю. Для чтения конкретного отчёта текущий пользователь вообще не передаётся в сервис. Аналогично расчёт по произвольной кофейне доступен всем ролям. Это нарушает раздел 02 независимо от того, какие кнопки скрывает UI.

Дополнительно `/dashboard/leader`, `/dashboard/city-leader` и `/ipv-triggers/statuses` передают в сервисы пустые массивы ID: выборки будут пустыми даже при наличии назначений и данных.

Источники: [reports controller](C:/LRT/backend/src/reports/reports.controller.ts:29), [dashboard controller](C:/LRT/backend/src/dashboard/dashboard.controller.ts:21), [IPV controller](C:/LRT/backend/src/ipv-triggers/ipv-triggers.controller.ts:37), [scoring controller](C:/LRT/backend/src/scoring/scoring.controller.ts).

### 3. Форма не обеспечивает создание и полное сохранение отчёта

- `saveDraft` не передаёт обязательный `coffeeShopId`.
- Если отчёта ещё нет, обработчики полей сразу выходят; создать первый заполненный отчёт этим путём нельзя.
- Берётся `reports[0]` без выбора назначенной кофейни и отчётного периода.
- Предыдущий факт всегда возвращает null. Поля плана не имеют обработчика сохранения; отдельного хранения планов в схеме нет.
- В форме нет полного набора денежных и вспомогательных показателей: выручки/напитков, подарков, персонала, аренды, оборудования и т. д. Есть лишь строки справочника рейтинговых метрик; это не эквивалент полного отчёта из документа 05.
- Текстовые вопросы отображаются только в разделе SUMMARY. Ответы анализа остальных четырёх блоков вводить негде.
- После отправки поля disabled, хотя ТЗ разрешает редактирование весь следующий месяц.
- «Образец заполнения» ведёт на `example.com`; настройки общей ссылки и работы с per-shop ReportLink через форму нет.
- Ошибки отдельных сохранений проглатываются; пользователь может не узнать, что данные не сохранены.

Источники: [загрузка и сохранение](C:/LRT/frontend/src/pages/leader/LeaderReportPage.tsx:107), [черновик](C:/LRT/frontend/src/pages/leader/LeaderReportPage.tsx:192), [поля](C:/LRT/frontend/src/pages/leader/LeaderReportPage.tsx:272), [схема](C:/LRT/backend/prisma/schema.prisma).

### 4. Расчёт рейтинга расходится с документом 03

- Во frontend используется `total / (metrics.length * 13) * 100`. По ТЗ рейтинг — сумма баллов. Для 10 метрик и 100 набранных баллов эта формула даёт 77.
- В `seed.cjs` производительность получает 11,5/5,75 вместо 8,5/4,25. Максимальная сумма исходной конфигурации равна 103, а должна быть 100.
- Пороги производительности не выбираются по четырём диапазонам `drinksCount`: используется фиксированная пара.
- Frontend сравнивает абсолютную сумму с процентными порогами, не рассчитывая долю выручки.
- `ReportsService.updateMetricValue` вычисляет процент для `HIGHER_IS_BETTER`, в том числе eNPS; долевые показатели в seed имеют `LOWER_IS_BETTER`.
- `maxPoints` backend вычисляет как количество метрик × баллы первой метрики, что неверно при разных группах баллов.
- При отправке отчёта расчёт не вызывается. UI дублирует собственные формулы вместо использования серверного результата.
- В Prisma параллельно существуют `thresholdStrong/pointsStrong` и `targetValue/ptTarget`. Админская форма меняет вторую группу, серверный scoring читает первую; добавление метрики из формы не передаёт обязательные поля первой группы.
- Деактивированные метрики возвращаются общим `/metrics`; экраны формы/результатов не отфильтровывают их как активные.

Источники: [frontend formula](C:/LRT/frontend/src/pages/leader/LeaderResultsPage.tsx:46), [seed](C:/LRT/backend/prisma/seed.cjs:120), [scoring](C:/LRT/backend/src/scoring/scoring-engine.service.ts:29), [проценты](C:/LRT/backend/src/reports/reports.service.ts:82), [admin payload](C:/LRT/frontend/src/pages/admin/AdminMetricsPage.tsx:90), [metrics service](C:/LRT/backend/src/metrics/metrics.service.ts).

### 5. Неизменность истории и журналы не обеспечены

Снапшотов применённых порогов/баллов нет в схеме. Scoring GET берёт текущие активные метрики и перезаписывает `zone/pointsAwarded`, не проверяя `isLocked`. Изменение конфигурации может изменить прошлый рейтинг. Frontend также каждый раз считает историю по текущим метрикам.

`logEdit` и `logConfigChange` существуют, но поиск по backend/src не обнаружил их вызовов из операций изменения. Поэтому наличие таблиц/экранов журналов не означает ведение аудита.

Черновик через upsert не проверяет блокировку и сбрасывает статус в NOT_FILLED. Отправка не проверяет полноту значений/анализа. Пошаговые операции сохранения/расчёта не объединены в общую транзакцию.

Источники: [scoring](C:/LRT/backend/src/scoring/scoring-engine.service.ts:21), [draft](C:/LRT/backend/src/reports/reports.service.ts:42), [submit и logEdit](C:/LRT/backend/src/reports/reports.service.ts:105), [config log](C:/LRT/backend/src/admin/admin.service.ts:24).

### 6. Неверные дедлайн и месяц блокировки

Просрочка настроена выражением `0 0 10 * *`: 00:00 десятого числа, а нужна 12:00 МСК. Выбирается текущий календарный месяц вместо предыдущего отчётного.

Блокировка первого числа выбирает предыдущий месяц вместо месяца X−2. Например, 1 сентября код блокирует август, хотя должен закрыть июль и оставить август редактируемым до конца сентября. Пропущенные старые периоды отдельно не подбираются.

Источники: [cron](C:/LRT/backend/src/common/jobs/scheduled-tasks.service.ts:11), [lock](C:/LRT/backend/src/common/jobs/scheduled-tasks.service.ts:46). Во frontend дедлайн дополнительно рассчитывается в локальной временной зоне браузера.

### 7. ИПВ пока представляет собой справочники и экран

В `IpvTriggersService` нет анализа рейтингов или создания IPVStatus. Нет вызова из cron/submit/scoring, который реализовал бы T1/T2/T3 и уведомления. Модель не содержит даты утверждения лидера в должности и настроек двух исключений по стажу; T3 не хранит ссылку на конкретную проблемную метрику.

UI отправляет PATCH `/ipv-triggers/statuses/:id`, backend слушает `/ipv-triggers/status/:id`. UI ждёт статус NEW, backend хранит NOT_STARTED; ждёт поля `rule`, `severity`, `daysOverdue`, которые API не формирует. Уведомления не связаны с автоматическим срабатыванием и открытием ИПВ.

Источники: [IPV service](C:/LRT/backend/src/ipv-triggers/ipv-triggers.service.ts), [controller](C:/LRT/backend/src/ipv-triggers/ipv-triggers.controller.ts), [экран](C:/LRT/frontend/src/pages/city-leader/CityTriggersPage.tsx).

### 8. Дашборды и доступ COO требуют завершения

COO закрыт доступ к `/metrics`, `/structure`, `/config`, `/history`, `/users` в маршрутах frontend: они разрешены ADMIN. API изменения ролей/назначений и списка пользователей также ограничен администратором. Это не соответствует праву COO управлять системой из документа 07.

На экранах захардкожены границы 80/60, хотя они должны читаться из RatingColorConfig. Получение этой настройки разрешено только COO/Admin, что требует отдельного безопасного чтения для лидеров.

История результатов лидера строится из последних записей всех кофеен вместе, а таблица «История периодов» оставляет по одной последней записи на кофейню. Среднее за год по заполненным месяцам не реализовано на этом экране; комментарии руководителей здесь не выводятся.

Источники: [маршруты](C:/LRT/frontend/src/App.tsx), [результаты](C:/LRT/frontend/src/pages/leader/LeaderResultsPage.tsx:117), [города COO](C:/LRT/frontend/src/pages/coo/CooCitiesPage.tsx:95), [карточка отчёта COO](C:/LRT/frontend/src/pages/coo/CooReportViewPage.tsx).

### 9. Импорт и нормализация чисел ненадёжны

Парсер пропускает лист с названием «Метрики» и читает остальные листы как название в A, значение в B. Документ 11 требует парсинг известной структуры мастер-листа «Метрики» с историей месяцев. Текущий импорт нельзя считать переносом реального формата.

Проверен непосредственно `backend/src/imports/import.parser.ts` через транспиляцию в памяти и вызов экспортированной функции:

- `4,19` → `4`, без сообщения о проблеме.
- `81 300,25 ₽` → `81300`, без сообщения о потере копеек.
- `12abc` → `12`, без ошибки.
- `1.2.3` → `1.2`, без ошибки.

Требуются нормализация запятой и проверка всей строки, а не принятие числового префикса через parseFloat. Аналогичный ввод в форме использует type=number/parseFloat. Проверка формата нужна и на сервере: TypeScript-типы inline body не являются runtime-валидацией DTO.

Источники: [структура импорта](C:/LRT/backend/src/imports/import.service.ts:24), [парсер](C:/LRT/backend/src/imports/import.parser.ts:66), [подтверждение](C:/LRT/backend/src/imports/import.service.ts:90).

## Порядок оставшихся работ

1. **Авторизация и права:** единый контракт токена, единый user.id, корректный Google callback, реальные назначения, серверные проверки доступа ко всем объектным операциям, сценарий сброса пароля.
2. **Расчёт и данные:** один набор полей метрик, веса 11,5/8,5, производительность по напиткам, проценты от выручки, единый серверный результат и снапшоты, атомарное сохранение/пересчёт и аудит.
3. **Полный месячный отчёт:** выбор кофейни/периода, создание черновика, все факты/планы/вопросы, ссылки, явные ошибки сохранения, серверная валидация, корректные cron и окно редактирования.
4. **Руководители и админка:** редактирование отчёта городом/COO, сводки и динамика метрик, средние по заполненным месяцам, общие цвета, комментарии лидеру, все согласованные настройки.
5. **Автоматический ИПВ:** T1/T2/T3, рост, стаж, исключения, события, баннеры, 14-дневная просрочка, согласованный контракт статусов и маршрутов.
6. **История и запуск:** парсер реального шаблона, контроль импорта/закрытых периодов, сверка 2–3 кофеен с эталоном, тесты настоящих сервисов и API с БД, CI, инструкция и комплект развёртывания, ручная приёмка четырёх ролей и мобильного UI.

## Что не считать недоделкой v1

По документам 08/11 можно отложить внешние интеграции с финансовыми системами/1С/RocketData, email/мессенджер-уведомления о событиях, экспорт сводок CSV/Excel, tooltip порогов в форме, индивидуальные пороги по городам и полноценные overrides по категориям. Это не отменяет email-сброс пароля, отдельно требуемый для входа.

Не нужны отдельное мобильное приложение, перемещение кофейни между городами, ручное закрытие периода, настраиваемая матрица прав и проведение самого ИПВ внутри сервиса.
